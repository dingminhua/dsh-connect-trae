# 缓存仍在生效，只是不再上报：`cache_read_input_tokens` 恒为 0 的计费侧证据

> 关联：#67（现象报告）、#10（2026-09-22 的同类问题，已修）
> 取证日期：2026-10-29 · 插件版本：4.6.3 · 平台：Windows 10.0.22621 · Trae CN

## 摘要

**Trae 上游的前缀缓存在 2026-10-29 仍在生效，并且仍按缓存价结算，但它不再通过 `token_usage.cache_read_input_tokens` 上报。**

#67 的结论是「上游没给这些请求分配缓存池，0% 是正确读数」。这个结论的前半段（`prompt_cache_pool_record` 恒为 `null`、`cache_read_input_tokens` 恒为 0）我完全复现了；但**后半段「所以没有缓存」不成立** —— 因为**账单不这么说**。

同一个 146k token 的请求，冷启动扣 **5.84 积分**，热启动只扣 **0.12 积分**。比值 `0.0205`，与 Trae 官方价目表里 deepseek 的「缓存读取 ÷ 输入」= `$0.006 ÷ $0.30` = `0.0200` **吻合到小数点后三位**。

也就是说：**钱是按缓存价收的，字段却报 0。** 这是一个**上报缺口**，不是「没有缓存」。

## 一、历史会话：Trae 曾经报得很好，然后断了

扫描本机 `~/.dsh/sessions` 下全部 **336 个会话日志**（解压 zstd，命中 34,996 行 `cacheReadTokens`），按 provider 聚合：

| provider / model | 步数 | 命中步数 | token 命中率 |
| --- | --- | --- | --- |
| `trae/glm-5.3` | 282 | **279（98.9%）** | 93.7% |
| `trae/deepseek-v4.1-flash` | 119 | 41（34.5%） | 76.2% |
| `trae/qwen-3.7-plus` | 6 | 0 | 0% |

- **最后一次 Trae 缓存命中：2026-10-27 22:32**（`session-b19b6305`，`qfmodel`，`cacheReadTokens` 已达 14 万级）
- 之后 **103 步连续为 0**，持续到今天
- 这与 #67 里 `lcy362` 的独立观察「27 号下午开始没有缓存的」**完全一致**

对照组（同一台机器、同一个 DSH 宿主）：`workbuddy`、`glm`、`minmax`、`dsh-opencode-go` 等 provider 的 `cacheReadTokens` 全部正常非零，最高 985,344。**显示链路没坏，只有 trae 这一路归零。**

## 二、关键实验：看钱，不看字段

字段会说谎，账单不会。所有实验都用**插件自己的只读用量接口**读 `summary.consumedAmount`，每次读账前等 16–25 秒结算窗口，避免一笔扣费被算到下一次读数上。

### 2.1 交错 A/B：排除「计费延迟」

两个**全新**前缀 A、B（UUID nonce 保证从未发送过），顺序 `A1 → B1 → A2 → B2`：

```
deepseek-v4.1-flash, 146k prompt, settle 20s
[A1 cold] prompt=146038 cache_read=0  creditsDelta=5.84
[B1 cold] prompt=143038 cache_read=0  creditsDelta=5.73
[A2 warm] prompt=146038 cache_read=0  creditsDelta=0.12
[B2 warm] prompt=143038 cache_read=0  creditsDelta=0.12
```

两个冷请求都约 5.8，两个热请求都 0.12。**交替顺序**排除了「第二个请求总是便宜」这种假象；第三次跑更便宜（0.14）也排除了延迟记账。

### 2.2 比值对得上官方价目表

| 模型 | 冷（积分） | 热（积分） | 实测比值 | 官方缓存读/输入 | 省下 |
| --- | --- | --- | --- | --- | --- |
| `deepseek-v4.1-flash` | 5.84 | 0.12 | **0.0205** | `0.006/0.30 = 0.0200` | 97.9% |
| `glm-5.3` | 35.75 | 8.66 | 0.2422 | `0.26/1.4 = 0.1857` | 75.8% |

价格来自 [TRAE 内置模型价目表](https://docs.trae.ai/ide/models?_lang=zh)。deepseek 吻合到小数点后三位；glm-5.3 方向一致（可能叠加了会员补贴系数）。

### 2.3 真实 DSH 请求形状也吃到了折扣

用当前会话自己的 `request/header`（74 个 tools）重放：

```
[dsh-shape run 1] prompt=24238 cache_read=0  creditsDelta=0.97
[dsh-shape run 2] prompt=24238 cache_read=0  creditsDelta=0.02
```

## 三、正面回应 #67 的「整请求复用，不是前缀缓存」

维护者在 #67 用 TTFT 论证：「同一份 25k 前缀 + 不同后缀 → 2772ms（还是冷的）」「共享前缀帮不上忙，只有整条请求一模一样才快」。

我同时测了 **TTFT 和扣费**，三种形状（`deepseek-v4.1-flash`，约 35k prompt）：

| 形状 | prompt | cache_read | TTFT | **扣费** |
| --- | --- | --- | --- | --- |
| ① 整条请求重发 #1（冷） | 35039 | 0 | 3148 ms | **1.41** |
| ① 整条请求重发 #2 | 35039 | 0 | 999 ms | **0.03** |
| ② 同前缀 + **不同后缀** #1 | 35062 | 0 | 1010 ms | **0.04** |
| ② 同前缀 + **不同后缀** #2 | 35062 | 0 | 3153 ms | **0.03** |
| ③ 增长式对话 #1 | 35041 | 0 | 1486 ms | **0.04** |
| ③ 增长式对话 #2 | 35057 | 0 | 815 ms | **0.04** |
| ③ 增长式对话 #3 | 35073 | 0 | 3121 ms | **0.03** |

**TTFT 确实和「整条请求是否一模一样」相关**（形状 ① 从 3148 → 999，形状 ② 两个不同后缀一次 1010、一次 3153，来回抖）。**但扣费不是**：一旦前缀被预热，形状 ② 和 ③（尾部每轮都不同、没有任何两条请求逐字节相同）**全部落到 0.03–0.04**，和形状 ① 的热请求同一档。

所以 TTFT 快慢反映的是**上游的整请求响应复用**，而**扣费折扣反映的是前缀缓存**。这是两件事，#67 把前者当成了后者的证据。**「TTFT 没变快」不能推出「没有缓存」。**

### 3.1 增长式对话是最贴近真实用法的形状

真实 DSH agent 会话就是形状 ③：system 固定、历史累积、每轮追加新消息。实测 6 轮：

```
[turn 1] prompt=24347 creditsDelta=0.98
[turn 2] prompt=24363 creditsDelta=0.03
[turn 3] prompt=24379 creditsDelta=0.03
[turn 4] prompt=24395 creditsDelta=0.02
[turn 5] prompt=24411 creditsDelta=0.03
[turn 6] prompt=24427 creditsDelta=0.02
```

**第 1 轮 0.98 → 第 2 轮起 0.02–0.03，降了 30–50 倍，且没有任何两条请求逐字节相同。** 如果上游真的「只有整条请求一模一样才便宜」，这里第 2–6 轮应该和 0.98 同档。

## 四、为什么不是插件又坏了

这个坑 #10 踩过一次（插件丢字段），所以必须先排除复发：

- 4.6.3 里 `cache_read_input_tokens → prompt_tokens_details.cached_tokens` 的转发代码**都在**（`src/sse.ts:116`、`src/solo-bridge.ts:230-251`）
- 同一宿主下其它 provider 显示正常（见第一节对照组）
- 把当初产出命中数字的 `scripts/probe-cache-convention.mjs` 原样重跑：2026-09-22 第 2/3 轮是 **5248 / 9216**，2026-10-29 是 **0 / 0**
- 我今天新写的探测脚本（CN 两个账号 × glm-5.3 / glm-5.2 / deepseek-v4.1-flash × 9k–165k prompt × 有/无 tools × 有/无 `session_id` × 4 种 function）**全部 `cache_read=0`**

## 五、`prompt_cache_pool_record: null` 意味着什么

它确实恒为 `null`，我复现了。但结合扣费证据，它更可能表示**「这次请求没有挂到需要单独记账的缓存池」**，而不是**「没有缓存」** —— 因为缓存折扣明明发生了。

一个合理的解释（**推测，未证实**）：缓存池记录可能只在**按池单独计费**的场景下才填，而当前的折扣是**按前缀匹配直接折算进 `consumedAmount`** 的。这条需要 Trae 侧确认，我这边拿不到内部实现。

## 六、给用户的实际结论

1. **积分没有被白烧。** 缓存折扣仍在生效，`deepseek-v4.1-flash` 约省 98%，`glm-5.3` 约省 76%。
2. **DSH 界面上的「0% 缓存」是显示缺口，不是省钱失败。** 别为这个换模型或换工具。
3. **判断缓存是否生效，别用 TTFT、也别用字段，用积分扣减量。** 这是当前唯一可信的读数。
4. 只有**冷启动第一轮**是全价 —— 新会话/新前缀的第一轮必然贵，这属正常。

## 七、建议

**给插件侧（低成本、可观测性）**

1. 既然 `cached_tokens` 现在恒 0 而折扣真实存在，卡片/输入框读数里那行「缓存命中」建议**加一个说明**：当前上游不报该字段，显示 0 不代表没有命中。
2. 4.6.4 已经解码 `metadata` / `timing_cost`，很好。建议**再加一项**：把每次请求前后的 `consumedAmount` 差值（如果能低成本拿到）作为「本次实扣积分」显示出来 —— 这是当前唯一能反映真实缓存状态的数字。
3. `docs/ISSUE67_DIAGNOSIS.md` 的结论建议补一句限定：**「上游不分配缓存池」与「缓存折扣未生效」不是同一件事**，后者已被账单否证。

**给上游（Trae）**

`cache_read_input_tokens` 恒为 0 但按缓存价结算，会让所有依赖该字段的成本统计（包括 Trae 自家 IDE 的用量面板、社区插件 Trae Use Token 的命中率）**系统性失真**。建议恢复上报，或在 `metadata` 里给出实际折扣依据。
