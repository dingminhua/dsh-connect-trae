## v4.18.3（2026-11-16）

> **限流不再是「请求写错」。** 这一版修掉 issue #85：Trae 的 `3004` 限流被报成报文错误，而且在流中途丢了码，最后显示成通用的 `stream ended` 并被当成网络故障反复重试。

### 这个版本修了什么

用户看到的现象是一句没有信息量的报错，然后旧错误重试几次再失败。沿着链路查下去，一个**账号事实**（这个号被限流了）在四层里分别被当成了**报文事实**（你请求写错了）和**网络故障**（连接断了）：

| 层 | 原来怎么错的 |
| --- | --- |
| 分类 | `3004` 落到 `classifyTraeFailure` 的默认分支 → `400` / `client`，即「不可重试的报文错误」，而且没有文案 |
| 时序 | Trae 先发 `request_wait_in_queue` / `progress_notice`，**再**发 `3004`；而 peek 把 queue 也算「已受理」，于是 peek 早停一步，3004 变成「中途中断」，进不了真 HTTP 错误路径 |
| 边界 | `src/shim.ts` 的 `body.on('error')` 只写本地日志然后裸 `res.end()`，消息在环回边界被丢掉 |
| 结果 | 内核只看到「200 的流提前结束」→ 判 `TRANSPORT` → 重试 2–3 次 → 每次再撞同一堵墙 |

这和 4.18.1 修的 `4008` / `4017` 是同源问题：**Trae 自己的原文说的是限流，插件却按不可重试的报文错误读它。**

### 改了什么

1. **`3004` 并入限流档**（`429` / `soft_rate`）并补可读文案。`soft_rate` 本就在 `FAILOVER_KINDS` 里，所以这是**换账号**而不是重放同一个号。文案刻意不含「quota」——内核先查额度措辞、再查限流措辞，一个错字就会把限流误判成不可重试的 `QUOTA`。
2. **peek 的「已受理」收紧到 `delta` / `usage` / `done`**。`queue` / `progress` 只说明「进了队列」，不说明「有答案要来」。
   - **代价封顶**：真排队的请求要等几分钟，而环回应答 200 正是内核空闲计时的起点。所以额外等待是 2.5 秒的预算，且只在 Trae **已经确认过**请求之后才启用——什么都没说的上游仍然立刻失败。
   - **预算必须是截止时间**：Trae 排队期间每隔几秒发一条 `progress_notice`，所以「每次 read 给 2.5 秒」会被不断重置——实测把响应头扣住 6 秒，最坏约 160 秒。现在只在首次确认时盖一次绝对截止时间，同一场景回到 2.5 秒。
   - **不丢字节**：超时的那次 `reader.read()` 不能取消（取消就是取消整个 body），所以它连同 promise 一起移交给重放流。这条单独有测试：摘掉交接，队列后的第一个 chunk 就消失。
3. **中途失败改成带类型的 `TraeStreamFailure`**（`kind` / `status` / `traeCode`）。状态行改不了了，但 SSE body 还开着：shim 写一帧 OpenAI 形状的 `data: {"error":{...}}`，`openai` SDK 会抛 `APIError`，内核按文案认出 `RATE_LIMIT`。刻意不带 `[DONE]`——失败不是完成。
4. **中途失败也回写号池**。不修这条，前三条只是把报错文案改好：一个「200 之后才限流」的账号在池里仍是健康的，下一个请求照样排到它。

### 顺带：DSH 0.2.2-rc.3 同步（零代码改动）

积压的 rc.3 同步一并记进这一版。它本身不含任何代码改动——插件消费的 **13 个宿主包的运行时文件逐字节完全相同**，构建产物与已发布的 4.18.2 逐字节相同。唯一的类型面变化是 `dsh-client-ui-primitives` 多了两个图标，而本插件不 import 该包。
