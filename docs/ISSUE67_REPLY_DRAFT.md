## 结论先讲

**这不是插件丢了缓存数字，是 Trae 上游根本没给这些请求分配前缀缓存池。**

也就是说：**0% 是正确读数**。你在十个会话里看到的都一致，因为原因在上游，跟提问简单还是复杂没有关系。

最关键的一条证据是上游自己给的。Trae 的 SSE 流里有一个 `metadata` 事件，里面有个字段
`prompt_cache_pool_record` —— 它**非空**才代表这次请求挂了缓存池。我实测了 **CN/AI 两个区、4 个账号、
7 个模型、4 种 function、三种请求头**，这个字段 **100% 是 `null`**。

没有池，`cache_read_input_tokens` 就只能是 0。上游并没有少报，它是在明说「这次没有池」。

## 为什么能确定不是插件

这里有个前情：这个插件以前确实因为不转发缓存字段被报过一次（issue #10），那个已经修了、也发了版。
所以我先验证「是不是又坏了」：

- 已安装的 4.6.3 里 `cached_tokens` / `cache_read_input_tokens` 的转发代码**都在**；
- 同一个 DSH 版本里，`workbuddy` 和 `dsh-opencode-go` 的缓存命中**显示正常、非 0** —— 说明显示链路没坏，
  坏的只有 trae 这一路；
- 我把当初产出命中数字的那份脚本 `scripts/probe-cache-convention.mjs` 原样重跑，对照如下：

| 轮次 | prompt_tokens | 2026-09-22 实测 | 2026-10-28 实测 |
| --- | --- | --- | --- |
| 第 1 次 | 5258 | 0 | 0 |
| 第 2 次 | 9224 | **5248** | **0** |
| 第 3 次 | 9224 | **9216** | **0** |

同一份脚本、同一套请求头、逐字节相同的前缀 —— 变量只剩上游。

还有一个旁证：2026-10-25 那天，`trae-global` 在我的会话日志里**真的命中过**（`cacheReadTokens` 依次
2048 → 41600 → 45824 → 46720）。两天后归零。而 Trae IDE 的构建版本在这两天都是 `2.3.93438`，
**客户端没变**。

## 那 tps 浮动 60–80 是怎么回事

这个和缓存无关，但确实有个容易误会的现象：**同一句话重发，第二次明显变快。**

我测了首字节时间（`timing_cost.first_sse_event_time`）：

| 情况 | 首字节 |
| --- | --- |
| 同一条请求重发 | 冷 3097 ms → 热 1207 ms |
| 同一份 25k 前缀 + **不同后缀** | **2772 ms（还是冷的）** |
| 同一 system + **不同 user** | 2910 → 1096（重发）→ 新 user 又 1806 / 3124 |

**共享前缀帮不上忙，只有「整条请求一模一样」才快。** 所以这是上游的**整请求复用**，不是 token 级前缀缓存
—— 而整请求复用**不产生任何 `cached_tokens`**。它解释了你看到的延迟/tps 浮动，也解释了为什么命中率仍是 0。

顺带说，如果你拿「有没有变快」来判断缓存有没有生效，这条路在当前上游是行不通的。

## 我这边做了什么

功能上没什么可修的（数字本来就没被丢），但有一个**可观测性缺口**值得补：`metadata` 和 `timing_cost`
这两个事件以前被当成未知事件直接丢掉了，所以你只能看到「0%」，没法知道是「上游没给池」还是「插件丢了数」。

本版把这两个事件解码出来并写进日志：

```
dsh-connect-trae: upstream request diagnostics
  { model: 'deepseek-v4.1-flash', promptCachePoolRecord: null, pipeline: 'llm_raw_chat_v2' }
```

`prompt_cache_pool_record` 我特意区分了 `null`（明确说没有池）和「字段不存在」——这两件事含义不同。

也顺手守住了一个坑：`metadata` 现在是个被认识的事件了，如果 peek 阶段把它当成「上游已应答」，那么紧跟在
它后面的拒绝（比如 `1005` 未订阅）就会退化成截断的 200 流，也就是 issue #19 那个老毛病。所以 peek 显式
把诊断事件排除在「已应答」之外，并加了回归测试锁住。

## 给你的建议

- **不用再排查插件了**，0% 是当前上游的预期读数；
- 哪天上游开始分配池，`cached_tokens` 会自动恢复显示，插件侧不需要再改；
- 想看当时真实情况，日志里搜 `upstream request diagnostics` 即可。
